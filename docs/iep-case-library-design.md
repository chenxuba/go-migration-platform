# IEP 案例库与 AI 生成增强方案

## 背景

当前系统已经支持基于 PEP-3 测评结果和儿童训练记录生成：

- IEP 总计划
- 季度 / 半年 IEP
- 月度计划
- 周计划

这些计划目前主要依赖“当前测评结果 + 当前训练记录 + 提示词”生成。随着系统使用量增加，老师确认后的计划会越来越多，这些确认计划本身可以沉淀为机构自己的 IEP 案例库。

目标不是简单把文档存起来，而是建立“输入 - AI 初稿 - 老师修改 - 最终确认 - 后续完成情况”的闭环，让后续 AI 生成时可以参考相似儿童、相似能力阶段、相似训练表现下老师最终认可的计划。

## 核心结论

建议先做“案例库 + 相似案例检索”，不建议一开始直接训练模型。

原因：

- 案例库上线成本低，能直接复用现有大模型能力。
- 机构数据早期规模不够，直接微调模型收益不稳定。
- IEP 属于高专业度内容，老师修改痕迹和后续完成反馈比最终文本本身更有价值。
- 相似案例检索可以按机构隔离、按儿童能力阶段过滤，更容易控制质量和合规。

后续数据规模足够后，再考虑模型微调或偏好学习。

## 数据闭环

案例库的核心不是“保存最终计划”，而是保存以下对应关系：

```text
测评结果
+ 儿童基础信息
+ 最近训练记录
+ AI 初稿
+ 老师编辑后的最终确认稿
+ 老师修改差异
+ 后续周计划完成情况
+ 目标达成反馈
= 可复用的高质量 IEP 案例
```

每一次老师确认 IEP、月计划、周计划，都可以形成一条或多条案例记录。后续周计划的完成情况和目标达成情况继续回写到案例库，形成质量评价。

## 需要沉淀的数据

### 儿童画像

- 儿童 ID
- 机构 ID
- 年龄、性别
- 出生日期、测评日期
- 诊断或能力标签，如果系统后续支持
- 当前训练阶段
- 老师 ID

用于相似案例检索时，真实姓名不应进入向量内容，可以只保留脱敏后的年龄、性别、能力阶段等信息。

### PEP-3 测评结果快照

建议在确认计划时保存一份测评结果快照，而不是只保存测评记录 ID。

需要包含：

- 各分量表原始分
- 发展年龄
- 百分位或标准分
- 优势领域
- 弱项领域
- 行为表现摘要
- 儿童表现记录摘要
- 系统生成的测评解释摘要

保存快照的原因是：后续测评规则、解释逻辑、题库数据可能调整，案例库需要保持当时生成计划时的上下文稳定。

### 训练记录快照

生成计划时应保存最近一段时间的训练记录摘要：

- 最近训练时间范围
- 训练课程类型
- 训练项目
- 完成情况
- 老师备注
- 高频问题
- 已稳定能力
- 需要继续强化的能力

早期可以保存结构化摘要，不一定要保存完整原始训练记录。

### AI 初稿

每次生成后保存 AI 原始输出：

- IEP 总计划初稿
- 月度计划初稿
- 周计划初稿
- 使用的模型
- 使用的 prompt 版本
- 生成时间
- 生成参数

AI 初稿用于和老师最终稿对比，分析老师经常修改哪些地方。

### 老师最终确认稿

老师点击确认后，需要保存最终版本：

- 总 IEP 最终稿
- 月计划最终稿
- 周计划最终稿
- 计划状态
- 确认时间
- 确认老师

这个版本是后续 AI 生成最重要的参考材料。

### 老师修改差异

建议保存 AI 初稿与老师最终稿的差异。

可记录：

- 修改字段
- 修改前内容
- 修改后内容
- 修改类型：新增、删除、重写、调整顺序、调整难度、调整课程形式、调整日期
- 修改所在计划类型：IEP、月计划、周计划

这部分数据可以用来发现机构偏好，例如：

- 老师经常把目标写得更具体。
- 老师经常降低某些儿童的训练难度。
- 老师经常把课程形式从集体课改成个训。
- 老师经常把周计划内容拆得更细。

### 后续完成情况与质量反馈

周计划执行后，需要把结果回写到案例库：

- 每日完成情况
- 目标是否达成
- 是否延期
- 老师备注
- 家长反馈，如果后续支持
- 是否需要调整目标
- 计划质量评分：优秀、可用、需调整、无效

没有后续反馈时，系统只能知道“老师确认过”；有后续反馈后，系统才知道“这个计划效果怎么样”。

## 建议数据模型

下面是逻辑模型，实际表名和字段可以按现有 Go 服务规范调整。

### iep_case

案例主表。

| 字段 | 说明 |
|---|---|
| id | 案例 ID |
| tenant_id | 机构 ID |
| student_id | 儿童 ID |
| assessment_id | 测评记录 ID |
| plan_duration_months | 计划周期，3 或 6 |
| case_status | draft、confirmed、archived |
| quality_score | 后续质量评分 |
| quality_label | excellent、usable、needs_adjustment、invalid |
| confirmed_by | 确认老师 |
| confirmed_at | 确认时间 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

### iep_case_input_snapshot

生成输入快照。

| 字段 | 说明 |
|---|---|
| id | 快照 ID |
| case_id | 关联案例 |
| student_profile_json | 儿童画像快照 |
| assessment_result_json | 测评结果快照 |
| training_record_summary_json | 训练记录摘要快照 |
| source_prompt_version | prompt 版本 |
| created_at | 创建时间 |

### iep_case_plan_version

计划版本表。

| 字段 | 说明 |
|---|---|
| id | 版本 ID |
| case_id | 关联案例 |
| plan_type | iep、monthly、weekly |
| target_month_index | 月计划所属月份 |
| target_week_index | 周计划所属周 |
| version_type | ai_draft、teacher_confirmed、manual_saved |
| plan_json | 计划结构化 JSON |
| model_name | AI 模型 |
| prompt_version | prompt 版本 |
| created_by | 创建人，AI 或老师 |
| created_at | 创建时间 |

### iep_case_edit_diff

老师修改差异表。

| 字段 | 说明 |
|---|---|
| id | 差异 ID |
| case_id | 关联案例 |
| plan_type | iep、monthly、weekly |
| field_path | 字段路径，例如 rows[0].shortGoal |
| before_value | 修改前 |
| after_value | 修改后 |
| edit_type | add、delete、rewrite、difficulty_adjust、date_adjust |
| created_by | 修改老师 |
| created_at | 修改时间 |

### iep_case_outcome

执行反馈表。

| 字段 | 说明 |
|---|---|
| id | 反馈 ID |
| case_id | 关联案例 |
| plan_type | monthly、weekly |
| target_month_index | 月份 |
| target_week_index | 周次 |
| completion_json | 完成情况 |
| teacher_comment | 老师备注 |
| goal_achievement_level | 达成等级 |
| adjustment_needed | 是否需要调整 |
| created_at | 创建时间 |

### iep_case_embedding

向量索引表或向量库记录。

| 字段 | 说明 |
|---|---|
| id | 向量记录 ID |
| case_id | 关联案例 |
| tenant_id | 机构 ID |
| chunk_type | assessment_summary、plan_summary、outcome_summary |
| chunk_text | 脱敏后的检索文本 |
| embedding | 向量 |
| metadata_json | 检索元数据 |
| created_at | 创建时间 |

如果当前数据库暂时不支持向量类型，可以先用普通表保存 chunk_text 和 metadata，后续接入 Milvus、pgvector、Elasticsearch 或其他向量检索方案。

## 生成流程

### 当前流程

```text
测评记录 + 训练记录
-> 组装 prompt
-> AI 生成计划
-> 老师编辑
-> 老师确认
```

### 增强后流程

```text
测评记录 + 训练记录
-> 生成结构化输入摘要
-> 从案例库检索相似案例
-> 过滤低质量案例
-> 组装 prompt：当前输入 + 相似案例 + 机构偏好
-> AI 生成计划
-> 老师编辑
-> 老师确认
-> 保存新案例和修改差异
-> 周计划执行后回写完成情况
```

## 相似案例检索维度

建议同时使用结构化过滤和向量检索。

结构化过滤：

- 同机构优先
- 同计划周期优先
- 年龄差距控制在一定范围内
- 测评日期相近优先
- 弱项领域相似优先
- 训练课程类型相似优先
- 排除质量标签为无效的案例

向量检索内容：

- 测评结果摘要
- 儿童能力弱项摘要
- 最近训练记录摘要
- 老师最终确认计划摘要
- 后续完成情况摘要

最终排序可以综合：

```text
相似度得分
+ 案例质量得分
+ 同机构加权
+ 最近使用加权
- 无反馈或低质量案例惩罚
```

## Prompt 组装建议

生成时不要把大量历史案例原文直接塞给 AI。建议只取 3 到 5 个高质量相似案例，并做摘要。

Prompt 中可以包含：

- 当前儿童测评摘要
- 当前训练记录摘要
- 当前要生成的计划类型
- 相似案例摘要
- 相似案例中老师最终确认的目标写法
- 相似案例中的有效训练方法
- 相似案例中不建议重复的问题
- 当前机构格式要求
- 输出 JSON 结构要求

相似案例示例内容建议控制为：

```text
案例 A：
- 年龄：3岁2月
- 主要弱项：语言表达、社交回应
- 训练表现：请求表达需要语言提示，集体活动等待困难
- 老师最终目标写法：...
- 后续反馈：周计划完成度较好，目标难度合适
```

## 分阶段落地计划

### 第一阶段：确认计划沉淀为案例

目标：先把数据闭环保存下来。

需要做：

- 老师确认 IEP 时创建或更新案例。
- 保存测评结果快照。
- 保存训练记录摘要快照。
- 保存 AI 初稿。
- 保存老师最终确认稿。
- 保存计划周期、老师、机构等元数据。

这一阶段不需要做向量检索，也不需要改生成效果。

### 第二阶段：保存修改差异

目标：知道老师到底改了什么。

需要做：

- 保存 AI 初稿和老师确认稿之间的字段级差异。
- 支持 IEP、月计划、周计划三类计划。
- 提供后台查看某个案例的修改历史。

这一步可以帮助后续总结机构偏好。

### 第三阶段：相似案例检索增强生成

目标：让 AI 生成时参考高质量历史案例。

需要做：

- 为案例生成脱敏摘要。
- 接入 embedding。
- 实现相似案例检索接口。
- 生成 IEP、月计划、周计划时，把相似案例摘要加入 prompt。
- 记录本次生成使用了哪些案例，便于追踪效果。

这一阶段会开始提升生成质量。

### 第四阶段：加入执行反馈

目标：让系统知道哪些计划真的有效。

需要做：

- 周计划完成情况回写案例库。
- 老师可以给计划质量打标。
- 相似案例检索时优先选择高质量案例。
- 低质量案例不再进入 AI 参考上下文。

这一阶段可以让系统逐步变得更精准。

### 第五阶段：模型微调或偏好学习

目标：在数据足够后进一步贴合机构风格。

触发条件建议：

- 已确认案例数量足够多。
- 每个主要能力领域都有覆盖。
- 有明确的老师修改差异。
- 有足够后续完成反馈。
- 案例质量标签可信。

可选方向：

- 微调输出格式和机构写法。
- 基于老师修改差异做偏好学习。
- 训练机构专属目标推荐模型。

## 接口建议

### 保存确认案例

`POST /api/v1/iep/cases/confirm`

用于老师确认 IEP 后沉淀案例。

请求核心字段：

```json
{
  "assessmentId": 123,
  "studentId": 456,
  "durationMonths": 3,
  "inputSnapshot": {},
  "aiDraftPlan": {},
  "confirmedPlan": {},
  "planType": "iep"
}
```

### 保存计划版本

`POST /api/v1/iep/cases/{caseId}/plan-versions`

用于保存月计划、周计划或人工修改后的版本。

### 查询相似案例

`POST /api/v1/iep/cases/similar`

请求核心字段：

```json
{
  "assessmentId": 123,
  "durationMonths": 3,
  "planType": "iep",
  "limit": 5
}
```

返回建议只返回脱敏摘要，不直接返回学生姓名。

### 保存执行反馈

`POST /api/v1/iep/cases/{caseId}/outcomes`

用于周计划完成后回写完成情况。

## 和当前系统的结合点

当前已有相关文件：

- 前端 API：`institution-admin/src/api/edu-center/pep3-assessment.ts`
- IEP 弹窗：`institution-admin/src/pages/teacher-center/components/generate-iep-modal.vue`
- Go 模型：`services/education/internal/model/iep_plan.go`
- 执行计划保存服务：`services/education/internal/service/pep3_execution_plan_persistence_service.go`

建议后续开发时优先接入这些节点：

- IEP 生成完成后保存 AI 初稿。
- 老师点击确认生成 IEP 后保存确认案例。
- 老师保存月计划、周计划后保存计划版本。
- 周计划完成情况保存时同步更新案例反馈。
- AI 生成前增加“查询相似案例”的服务调用。

## 数据安全与合规

需要注意：

- 案例库必须按机构隔离。
- 默认只使用本机构案例。
- 不要把儿童姓名、手机号、证件号等敏感信息写入向量文本。
- 用于 AI prompt 的历史案例应脱敏。
- 支持管理员删除或归档案例。
- 对外部模型传输数据时，应只传生成所需的最小信息。

## MVP 验收标准

第一版可以按以下标准验收：

- 老师确认 IEP 后，系统能保存一条案例。
- 案例中包含测评结果快照、训练记录摘要、AI 初稿、老师最终稿。
- 老师再次编辑保存后，能保存新的计划版本。
- 周计划完成情况可以关联到案例。
- 后续生成 IEP 时，服务端可以查出 3 到 5 个相似案例摘要。
- prompt 中可以带入相似案例摘要。
- 不同机构之间案例默认不可见。

## 预期效果

短期效果：

- 生成结果更贴近机构已有写法。
- 老师重复修改的内容会减少。
- 月计划、周计划更容易和总 IEP 对齐。

长期效果：

- 系统能积累机构自己的 IEP 方法库。
- AI 可以参考真实确认案例，而不是只依赖通用提示词。
- 加入后续完成情况后，AI 能优先参考实际有效的计划。
- 数据足够后，可以进一步做机构专属模型优化。
